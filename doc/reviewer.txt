1. INTRODUCTION                                      *reviewer-introduction*

reviewer.nvim is a stripped-down, branch-scoped review layer for
codediff.nvim and vim-fugitive. Leave inline comments on a diff, then send
them all to sidekick.nvim in one keystroke.

Features:
- Inline comments on diff lines, with a floating input popup
- Multi-line comments on a visual selection
- File-level comments
- Comments stored per repository and branch
- Send every comment to sidekick.nvim as markdown, then clear them

================================================================================
2. REQUIREMENTS                                      *reviewer-requirements*

- Neovim >= 0.10
- codediff.nvim and/or vim-fugitive
- sidekick.nvim (only for sending)

No other UI dependency: the comment popup is a plain floating window.

================================================================================
3. INSTALLATION                                    *reviewer-installation*

With lazy.nvim: >lua
  {
    "you/reviewer.nvim",
    dependencies = {
      { "esmuellert/codediff.nvim", optional = true },
      { "tpope/vim-fugitive", optional = true },
      { "folke/sidekick.nvim", optional = true },
    },
    event = "VeryLazy",
    opts = {},
  }
<
Load the plugin before you open a review surface (VeryLazy or lazy = false).
The keys are buffer-local to the review buffers. reviewer.nvim follows the
current codediff tab: keys, marks, and comments apply to the active tab's
session.

sidekick.nvim is optional and loaded on demand: it is only required when
sending comments. The `optional = true` entries let lazy.nvim load a plugin
when it is used without force-loading it at startup.

Options: >lua
  opts = {
    sidekick = {
      -- sidekick tool that receives the comments; nil = sidekick's current tool
      tool = "copilot",
    },
    -- Keys are buffer-local to the codediff panes. Omit a key to keep its
    -- default; set it to false to disable that action.
    keys = {
      add_comment = "<localleader>a",
      file_comment = "<localleader>F",
      edit_comment = "<localleader>e",
      delete_comment = "<localleader>d",
      list_comments = "<localleader>c",
      next_comment = "]n",
      prev_comment = "[n",
      send_comments = "<localleader>S",
      close_review = "<localleader>q",
    },
  }
<

================================================================================
4. REVIEW SURFACES                                      *reviewer-surfaces*

Two surfaces are supported, through a source per surface:

codediff diff (both layouts) ~
  Positions come from the codediff lifecycle: the window tells the side, the
  session path tells the file.

fugitive `:Git` status buffer ~
  Positions come from the buffer text. A fugitive status buffer is a rendered
  view over git: file entries, section headings, and, once you expand a hunk
  with `>`, the real unified diff. A comment on a hunk line is stored as the
  *file* line and side, derived from the `@@ -a,b +c,d @@` header, so it
  survives `:Gwrite` and every status rebuild. A comment on a file entry line
  is a file-level comment (line 0). A comment whose hunk is collapsed shows a
  count on the file's entry line until the hunk is expanded again.

  Marks are re-derived from the buffer text after every rebuild and whenever a
  hunk is expanded or collapsed, so they never point at a stale line.

  Staged, Unstaged, and Untracked are separate scopes: the same file line
  appears in two sections with different content, so a staged comment and an
  unstaged comment on the same line are two different comments.

A source only has to map a buffer to `{ file, line, side, scope }`; the store,
the popup, the marks, and the send payload are shared. Forge review plugins
(octo, gitlab.nvim) are deliberately not sources: they own review-thread
identity on the server, so a local per-branch store would desynchronize.

5. KEYMAPS                                              *reviewer-keymaps*

In a codediff diff or a fugitive status buffer: >text
  <localleader>a   Add a comment at the cursor or range        key: add_comment
  <localleader>F   Add or edit a file-level comment           key: file_comment
  <localleader>e   Edit the comment at the cursor             key: edit_comment
  <localleader>d   Delete the comment at the cursor           key: delete_comment
  <localleader>c   List all comments and jump to one          key: list_comments
  ]n               Next comment                               key: next_comment
  [n               Previous comment                           key: prev_comment
  <localleader>S   Send all comments to sidekick, then clear  key: send_comments
  <localleader>q   Clear comments and close the review tab    key: close_review
<
Set a `key` option to `false` to disable that action.
The diff buffers stay editable: no key the plugin sets shadows a normal Vim
editing key, so you can fix the file in the codediff pane. In a fugitive status
buffer `close_review` clears the comments and detaches the keys; it does not
close the tab you opened it in.

The `add_comment` key also works in visual mode: select lines, then press it to
comment on the whole range. Ranges are line-based, so a character-wise
selection comments every line it touches. In a fugitive hunk the selection is
mapped to file lines, and a selection spanning both sides of the diff is
refused rather than guessed. The comment box sits under the last selected line
and the range is highlighted with the `ReviewerRange` highlight group (linked
to `Visual` by default). Edit and delete find a range comment from any line it
covers.

`<localleader>` is resolved when the keys are installed, that is when a
codediff session opens, so set `vim.g.maplocalleader` before you open
codediff.

Comment popup: |<C-s>| submits, |<Esc>| or |q| cancels.

================================================================================
6. STORAGE                                              *reviewer-storage*

One JSON store per repository and branch, in
`~/.local/share/nvim/reviewer/<repo>-<branch>.json`. Comments on one branch
never show on another. A codediff review and a fugitive status review of the
same branch share the store file, but each comment is scoped to its surface,
so a comment left on one surface does not appear on the other.

A comment's identity is `file`, `line`, `side`, and `scope`. `scope` is the
source's slice of the review: `staged`, `unstaged`, or `untracked` for a
fugitive status buffer, empty for codediff.

================================================================================
7. SENDING TO SIDEKICK                                    *reviewer-send*

|<localleader>S| sends a markdown list. Each comment is a reference line, then its
text on the next line, then a blank line: >text
  Code review comments on the current diff (`~` = old side).

  1. `src/api.ts:23`
  endpoint does not handle errors

  2. `src/utils.ts:~10`
  old implementation was cleaner

  3. `src/api.ts`
  whole file needs a pass

  4. `src/db.ts:8-19`
  this block duplicates the retry logic

<
A `~` before the line number marks the old (left) side of the diff; the header
only mentions it when such a comment is present. Inline diffs never produce one,
since the original pane is not shown. A bare path
is a file-level comment. `start-end` is a multi-line comment.
Comment text is flattened to one line. After sending, all comments
and their inline marks are removed.

The payload is built as sidekick text, so new-side comments are sent as that
tool's own file reference (`@file#L10-20` for Claude, `@file :L10-L20`
elsewhere) and expand to the file. Old-side comments keep the `file:~10` form,
since a reference would point at the current file where that line no longer
exists.
